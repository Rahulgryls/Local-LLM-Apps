SECTION 1 — SYSTEM OVERVIEW & ARCHITECTURE
================================================================================

WHAT IS LAKO?
─────────────
LAKO (Local AI Knowledge Orchestrator) is a fully on-premises AI knowledge
platform built for Rabobank's internal use. It allows users to:
  - Ingest PDF, DOCX, PPTX, XLSX, HTML, and Confluence pages into a local
    vector database.
  - Ask natural-language questions against those documents (RAG).
  - Search the web via a self-hosted SearXNG instance.
  - All AI inference runs locally via Ollama — no external API calls.

STACK
─────
  Backend : FastAPI (Python 3.11), aiosqlite, qdrant-client, PyMuPDF,
            pdfplumber, python-docx, python-pptx, openpyxl, BeautifulSoup4,
            httpx, structlog
  Frontend: React 18, Zustand, Tailwind CSS, Lucide icons, react-i18next
  AI      : Ollama (local), qwen3.5:35b-a3b-coding-nvfp4 (LLM + vision),
            nomic-embed-text (768-dim embeddings), qwen2.5:3b (summarisation)
  Storage : Qdrant (embedded, no Docker), SQLite (two DBs), filesystem

ARCHITECTURE — HIGH LEVEL
─────────────────────────

  Browser (React SPA)
      │
      ▼  HTTP / SSE
  FastAPI Backend (port 8000)
      │
      ├── Ingestion routers (V2 + V3)
      │       │
      │       ├── File extractors → SQLite (lako_v2.db)
      │       ├── LLM Summariser  → Ollama
      │       └── Embedder        → Qdrant (storage/qdrant/)
      │
      ├── RAG router (/api/v2/query)
      │       │
      │       ├── Embedding cache → Ollama embed
      │       ├── Dual Qdrant search (lako_page_summaries + lako_documents)
      │       ├── MMR diversity pass
      │       ├── Context fetcher (SQLite + Qdrant payload fallback)
      │       ├── Budget manager (token trimming)
      │       └── LLM stream → SSE → Browser
      │
      └── Dashboard / Settings / Health endpoints

QDRANT COLLECTIONS
──────────────────
  lako_page_summaries  — V2 pipeline: stores LLM-generated summaries of each
                         page (PDF/PPTX/DOCX). One point per page.
                         Payload: doc_id, page_num, filename, source_type,
                                  headers, has_tables, summary_text

  lako_documents       — V3 pipeline + Confluence V3: stores raw text chunks
                         directly (no summarisation pass).
                         Payload: doc_id, source_id, filename, source_type,
                                  block_type, page, url, text

SQLITE DATABASES
────────────────
  storage/lako_v2.db  — V2 pipeline
    Tables: documents, pages, page_summaries

  storage/lako.db     — V3 pipeline + Confluence V3
    Tables: documents, document_chunks

INGESTION PIPELINES
───────────────────
  V2 Pipeline (PDF, PPTX, DOCX via /api/v2/ingest):
    Pass 1: Structure extraction → SQLite pages table
    Pass 2: LLM page summarisation (qwen2.5:3b) → page_summaries table
    Pass 3: Embed summaries (nomic-embed-text) → lako_page_summaries Qdrant

  V3 Pipeline (PDF, DOCX, PPTX, XLSX, HTML via /api/v3/ingest):
    Pass 1: Per-page classifier (TEXT_RICH / TABLE / IMAGE_ONLY / MIXED)
    Pass 2: Extract text / flatten tables / vision-describe images
    Pass 3: smart_chunk() → 400-token sentence-boundary chunks
    Pass 4: Embed chunks → lako_documents Qdrant

  Confluence V3 Pipeline (via /api/v3/ingest/confluence):
    Crawl: BFS from root page, collect all child page IDs
    Per-page: Fetch HTML → BeautifulSoup parse → text/table/code chunks
    Embed: nomic-embed-text → lako_documents Qdrant

RAG QUERY PIPELINE
──────────────────
  POST /api/v2/query
    1. Cache check (LRU-50, 1-hour TTL)
    2. Embed query with nomic-embed-text (embedding cache)
    3. Dual Qdrant search: lako_page_summaries + lako_documents
       (limit = top_k × 5 per collection for MMR oversampling)
    4. Merge results, sort by score descending
    5. MMR diversity pass:
       - Pass 1: Guarantee max(1, top_k//num_docs) slots per doc (threshold-free)
       - Pass 2: Fill remaining slots meeting score_threshold, per-doc cap
    6. Context fetch: get raw page text from SQLite (or Qdrant payload for V3)
       with optional ±buffer_pages neighbours
    7. Budget trim to 12,000 token limit:
       - Drop buffer pages low-score first
       - Drop all buffers
       - Truncate lowest-scored direct matches to 4000 chars
    8. Build prompt: pages grouped by doc, wrapped in === delimiters
    9. Stream LLM response via SSE
    10. Cache response async

DOCUMENT DEDUPLICATION
──────────────────────
  Both V2 and V3 use SHA-256 content hashing.
  If hash matches an existing ready/indexed doc → skip, return existing doc_id.
  If same filename but different hash → "ingest-first, swap-after":
    New doc is fully indexed before old doc is evicted from Qdrant + SQLite.
    This ensures zero downtime during document updates.

FRONTEND STATE
──────────────
  Zustand store (appStore.js) holds:
    - Chat messages, ragMode, selectedDocId, showDebug (persists across
      navigation — chat history survives page switches)
    - Model names, vector stats, ingestion status, settings

  Ephemeral state (local useState in Chat):
    - Loading/streaming flags, input prompt, scroll state

6a. backend/ingestion/orchestrator.py  (V2 Pipeline Orchestrator)
────────────────────────────────────────────────────────────────────────────────

Entry point for all V2 document ingestion (PDF, PPTX, DOCX).
Called by ingest_v2 router via BackgroundTasks.

FUNCTION: ingest_document(file_path, source_type, progress_callback, original_filename) -> str
  Returns doc_id.

FLOW:
  1. SHA-256 hash → deduplicate (if identical content exists as "ready", return existing doc_id)
  2. Check for same filename (prev doc) — store reference but do NOT delete yet
  3. Create documents row (status=processing)
  4. Pass 1 — extraction:
       pdf  → extract_pdf()   (PyMuPDF + pdfplumber for tables)
       pptx → extract_pptx()  (python-pptx)
       docx → extract_docx()  (python-docx)
     Results stored in SQLite pages table.
  5. Pass 2 — summarisation (batch_size=1 for reliability):
       For each page: summarize_page() → LLM call → stored in page_summaries
  6. Pass 3 — embedding:
       ensure_collection() → _embed_all_summaries_for_doc()
       → embed each summary → upsert to lako_page_summaries Qdrant
  7. status = ready
  8. Evict old doc (if prev): delete old Qdrant vectors + old SQLite rows

PROGRESS CALLBACK: fn(doc_id, phase, current, total)
  Phases: "extracting", "summarizing", "embedding"

SUPPORTED EXTENSIONS: .pdf, .pptx, .docx

6b. backend/ingestion/pdf_extractor.py  (V2 PDF Extraction)
────────────────────────────────────────────────────────────────────────────────

Uses PyMuPDF (fitz) as primary extractor.
Uses pdfplumber as targeted secondary pass for table pages only.

TABLE DETECTION HEURISTIC (avoids calling pdfplumber on every page):
  _looks_like_table_page(text) returns True if:
    - Line has 2+ pipe chars (|)
    - Line has 2+ consecutive tab chars
    - Line has 3+ short tokens separated by 2+ spaces (column-like layout)
  Only if heuristic fires → pdfplumber called to confirm and extract table.

HEADER DETECTION (_extract_headers):
  Uses PyMuPDF font-size analysis.
  Spans > avg_size + 1.5pt above average → treated as headers.
  Capped at 10 headers per page.

SCANNED PAGES (< 50 chars text):
  Render page to PNG at 2× zoom (144 DPI) → vision model OCR.

FUNCTION: extract_pdf(file_path, doc_id, progress_callback) -> int (total pages)

6d. backend/ingestion/docx_extractor.py  (V2 DOCX Extraction)
────────────────────────────────────────────────────────────────────────────────

Splits Word document into virtual "pages" at heading boundaries (H1–H4).
Sections > 5000 chars split at paragraph boundaries.

TABLE HANDLING: _flatten_table()
  First row = headers. Subsequent rows formatted as:
    "Header1: Val1 | Header2: Val2"
  Tables get their own virtual page (flushed before + after table).

IMAGE HANDLING: _vision_describe()
  Embedded images extracted via doc.part.rels
  Image bytes → base64 → vision model → text description appended as final pages.
  Tiny images (< 500 bytes) skipped.

FUNCTION: extract_docx(file_path, doc_id, progress_callback) -> int (virtual pages)

6e. backend/ingestion/summarizer.py  (V2 LLM Summarisation)
────────────────────────────────────────────────────────────────────────────────

Generates 2–3 sentence summary per page using LLM.
Uses summarization_model (qwen2.5:3b) or falls back to primary_model.

EDGE CASES:
  Empty page (< 50 chars)  → stored as "[Empty page]"
  Page > 6000 chars        → truncated before sending, "(truncated)" appended
  LLM timeout/error        → one retry, then "[Summarization failed]"

PROMPT TEMPLATE:
  "Summarize this page in 2-3 sentences.
   Preserve: key entities, numbers, policy names, decisions, relationships.
   Be specific — use names, dates, and figures from the text.
   Document: {doc_name}, Page {page_num} of {total_pages}
   Headers: {headers_str}
   ---
   {raw_text}"

_clean_summary(): strips echoed page headers/separators, hard-caps at 1500 chars.

BATCH SUMMARISATION (summarize_batch):
  Groups up to 3 pages per LLM call using ---PAGE_BREAK--- separator.
  Current batch_size = 1 (reliability mode; batch logic preserved for future).

FUNCTIONS:
  summarize_page(doc_id, page_num, raw_text, headers, doc_name, total_pages) -> str
  summarize_batch(pages: list[dict]) -> list[str]

6g. backend/ingestion/service.py  (V3 Direct-RAG Pipeline)
────────────────────────────────────────────────────────────────────────────────

No LLM summarisation — raw text preserved exactly.
Vision model called only for IMAGE_ONLY pages and MIXED image regions.

COLLECTION: lako_documents
VECTOR_SIZE: 768

PAGE CLASSIFIER (_classify_page):
  TEXT_RICH  : token_count >= 50 (sentence-boundary chunking)
  TABLE      : _looks_like_table() triggered at any token count
  IMAGE_ONLY : token_count < 20 AND has images (render + vision)
  MIXED      : token_count >= 20 AND has images (text direct + vision per image)

SMART CHUNKING (smart_chunk):
  Split text on sentence boundaries (". ", "? ", "! ", "\n\n").
  Max 400 tokens per chunk (whitespace-split words).
  50-token overlap carry-over between chunks.
  Tables: always kept as single chunk (never split).
  Returns list of (chunk_text, metadata_copy).

PDF PAGE PROCESSING (_process_pdf_page):
  TEXT_RICH  → smart_chunk(raw_text, meta{block_type="text"})
  TABLE      → pdfplumber flatten → smart_chunk(table_text, meta{block_type="table"})
               fallback to text if pdfplumber finds no table
  IMAGE_ONLY → render page PNG @ 150dpi → vision_call() → single chunk
  MIXED      → text chunks + vision call per image rect (skip if < 50×50 px)

EMBED AND STORE (_embed_and_store):
  For each chunk: embed text → upsert Qdrant point → insert SQLite chunk row.
  Qdrant point payload: all metadata + "text": chunk_text.
  One bad chunk does not abort the document (continue on error).

INGEST FLOW (ingest_file):
  Stage 1: SHA-256 hash dedup
  Stage 1b: Find prev by filename (ingest-first, swap-after)
  Stage 2: Route to correct pipeline (pdf/docx/pptx/xlsx/html)
  Stage 3: Parse → list of (text, metadata) tuples
  Stage 4: Copy original file to storage/documents/{doc_id}/original.{ext}
  Stage 5: _ensure_collection() → _embed_and_store()
  Stage 6: Evict old doc (if prev) after new is verified (chunk_count > 0)

SUPPORTED TYPES: pdf | docx | pptx | xlsx | html

FUNCTIONS:
  smart_chunk(text, page, metadata, max_tokens=400, overlap=50) -> list[(str, dict)]
  ingest_file(file_path, filename, source_type, progress_callback) -> dict
    Returns: {"doc_id", "status": "duplicate"|"indexed"|"replaced", "chunks", "pages"}
  source_type_from_filename(filename) -> str

6h. backend/ingestion/docx_pipeline.py  (V3 DOCX + HTML)
────────────────────────────────────────────────────────────────────────────────

DOCX PIPELINE (docx_pipeline):
  Walks doc.element.body to see paragraphs AND tables in document order.
  Sections split at heading styles ("Heading 1"-"Heading 4").
  Tables flattened to "Col: Val | Col: Val" rows → block_type="table".
  Embedded images extracted from doc.part.rels → vision model → appended.

HTML PIPELINE (html_pipeline):
  Used for Confluence HTML export files.
  BeautifulSoup parse → headings / tables / paragraphs / lists.
  Tables: flatten rows using header row as keys.
  Min 5 tokens per chunk (shorter text discarded).

────────────────────────────────────────────────────────────────────────────────
6i. backend/ingestion/pptx_pipeline.py  (V3 PPTX)
────────────────────────────────────────────────────────────────────────────────

Uses python-pptx. Each slide classified as TEXT_RICH/TABLE/IMAGE_ONLY/MIXED.
Image-only slides rendered to PNG via LibreOffice (brew install libreoffice).
LibreOffice not found → IMAGE_ONLY slides stored empty with warning.
Speaker notes always extracted and appended to slide text.

────────────────────────────────────────────────────────────────────────────────
7a. backend/retrieval/searcher.py
────────────────────────────────────────────────────────────────────────────────

DUAL-COLLECTION VECTOR SEARCH + MMR DIVERSITY

COLLECTIONS SEARCHED:
  lako_page_summaries — V2 pipeline (PDFs, PPTX, DOCX)
  lako_documents      — V3 pipeline (Confluence, newer file uploads)

FUNCTION: search_pages(query, top_k=5, score_threshold=0.3,
                       doc_id_filter=None, source_type_filter=None,
                       query_vector=None) -> list[SearchResult]

FLOW:
  1. Embed query (or use pre-computed query_vector)
  2. Build optional Qdrant filter (doc_id and/or source_type)
  3. Query lako_page_summaries with limit=top_k*5
  4. Query lako_documents with limit=top_k*5 (if collection exists)
  5. Merge all hits, sort by score descending
  6. Apply MMR diversity → return up to top_k results

MMR DIVERSITY ALGORITHM (_apply_mmr_diversity):

  Purpose: Prevent one document from monopolising all slots when multiple
  documents are indexed. Ensures minority-domain docs always contribute.

  Inputs: hits (sorted score desc), top_k, score_threshold

  Pass 1 — Guaranteed slots (THRESHOLD-FREE):
    guarantee_per_doc = max(1, top_k // num_unique_docs)
    Each unique document gets guarantee_per_doc slots unconditionally.
    Example: top_k=8, 3 docs → 2 guaranteed slots per doc = 6 total guaranteed
    These slots bypass score_threshold — the doc earned them by being indexed.

  Pass 2 — Fill slots (THRESHOLD ENFORCED):
    per_doc_cap = max(2, top_k // num_unique_docs)
    Remaining slots (up to top_k) go to highest-scoring hits that:
      a. Meet score_threshold
      b. Have not exceeded per_doc_cap for their document
    Stops when result list reaches top_k.

  Final sort by score descending.

SEARCH RESULT PAYLOAD NORMALISATION:
  V2 points: payload uses "summary_text" key
  V3 points: payload uses "text" key
  Normalised to SearchResult.summary_text for both.

────────────────────────────────────────────────────────────────────────────────
7b. backend/retrieval/context_fetcher.py
────────────────────────────────────────────────────────────────────────────────

FUNCTION: fetch_context(search_results, buffer_pages=1) -> AssembledContext
  (currently called with buffer_pages=0 in rag_v2.py)

STRATEGY:
  For each SearchResult at page N, fetch pages [N-buffer, N+buffer] clamped
  to [1, doc.total_pages].

  Deduplication: if a page appears in multiple windows:
    - Keep single entry
    - is_direct_match = True if it was directly returned by Qdrant
    - score = max(all associated scores)

  Sort all collected pages by (doc_id, page_num) for coherent reading order.

V3/Confluence fallback:
  V3 docs are NOT in lako_v2.db pages table.
  Falls back to text carried in SearchResult.summary_text (from Qdrant payload).

OUTPUT: AssembledContext
  pages:        list[PageContent] sorted by (doc_id, page_num)
  total_tokens: sum(len(raw_text)) // 4  (rough token estimate)
  sources:      unique [{doc_id, filename, page_num, score}] list

────────────────────────────────────────────────────────────────────────────────
7c. backend/retrieval/budget_manager.py
────────────────────────────────────────────────────────────────────────────────

FUNCTION: apply_budget(assembled: AssembledContext) -> AssembledContext

MAX_CONTEXT_TOKENS = 12,000  (safe for 20K num_ctx; leaves ~8K for output + system)
_TRUNCATION_CHARS  = 4,000   (chars kept when truncating a direct-match page)
_CHARS_PER_TOKEN   = 4       (rough estimate)

TRIM STRATEGY (stops as soon as budget met):

  Step 1 — Drop buffer pages lowest-score first:
    Buffer pages sorted by score ascending.
    Drop one at a time until within budget.
    Direct-match pages untouched.

  Step 2 — Drop ALL buffer pages:
    If still over budget after Step 1, discard all remaining buffers.
    Only direct-match pages remain.

  Step 3 — Truncate lowest-scored direct-match pages:
    Sort by score ascending.
    For each page that would exceed budget: truncate to min(remaining_budget * 4, 4000) chars.
    Append "\n[truncated]" marker.
    Pages < 100 chars after truncation → skip entirely.
    Direct-match pages are NEVER fully dropped.

Sources list is preserved unchanged (citations never trimmed).

8a. backend/routers/rag_v2.py  — POST /api/v2/query
────────────────────────────────────────────────────────────────────────────────

THE MAIN RAG ENDPOINT. Returns SSE streaming response.

REQUEST BODY (JSON):
  query        string  — Natural-language question
  language     string  — "en" | "nl" (default "en")
  rag_enabled  bool    — true=search docs, false=web search (default true)
  doc_id       string? — Filter to single document (bypasses query cache)

SSE RESPONSE FORMAT:
  data: {"token": "<chunk>", "done": false}    — one per LLM token
  data: {"token": "", "done": true, "sources": [...], "timing": {...}}  — final

Sources (RAG mode): [{doc_id, filename, page_num, score}]
Sources (web mode): [{title, url}]
Error event:        {"token": "", "done": true, "error": "...", "sources": []}

TIMING FIELDS (in final event):
  embedding_ms, search_ms, fetch_ms, assembly_ms, llm_first_token_ms, llm_total_ms
  OR {cache_hit: true} if served from cache.

RAG PIPELINE (_stream_rag):
  1. Query cache check (skip if doc_id filter active)
  2. Embed query (embedding cache)
  3. search_pages() → list[SearchResult]
  4. fetch_context(buffer_pages=0) → AssembledContext
  5. apply_budget() → trimmed context
  6. build_query_prompt() → (user_prompt, system_prompt)
  7. ollama_client.stream_chat() → token stream → SSE
  8. Async cache store (non-blocking)

WEB PIPELINE (_stream_web):
  1. web_search() → list[WebResult]
  2. build_web_prompt() → (user_prompt, system_prompt)
  3. ollama_client.stream_chat() → SSE

CACHES:
  query_cache    — LRU-50, 1-hour TTL. Stores {response: str, sources: list}.
                   Cleared on new document ingest.
  embedding_cache — Caches query vectors. Avoids re-calling Ollama embed.

================================================================================
SECTION 15 — KEY DESIGN DECISIONS
================================================================================

1. DUAL QDRANT COLLECTIONS
   lako_page_summaries stores LLM-generated summaries (V2 pipeline).
   lako_documents stores raw chunks (V3 pipeline + Confluence).
   Both are queried in every search and merged before MMR.
   Rationale: V2 summaries are more semantically dense for retrieval;
   V3 raw chunks are better for exact table/number retrieval.

2. INGEST-FIRST, SWAP-AFTER (atomic document replacement)
   When re-uploading an existing document, the new doc is fully indexed
   before the old one is deleted. This ensures zero downtime — queries
   against the old doc still work until the new one is ready.
   The old doc ID is recorded at start but deletion is deferred to the end.

3. MMR GUARANTEE SLOTS
   Standard MMR would score across all candidates and let one document
   dominate. LAKO's modified MMR guarantees max(1, top_k//num_docs) slots
   per document regardless of score. This is critical for a bank using
   documents from multiple domains (economic reports, HR policies, legal docs)
   where cross-domain cosine similarity is low.

4. SCORE THRESHOLD ONLY ON FILL SLOTS
   Guaranteed slots bypass score_threshold entirely. Only the "fill" pass
   enforces the threshold. This prevents minority-domain documents from being
   filtered out when their page summaries are semantically distant from the
   query domain.

5. V3 DIRECT-RAG (NO SUMMARISATION)
   V2 required LLM summarisation per page (slow, model-dependent quality).
   V3 skips summarisation entirely — raw text preserved in Qdrant payload.
   Trade-off: chunks are larger and less semantically focused, but ingest is
   much faster and text fidelity is perfect (important for exact figures).

6. PAGE CLASSIFIER IN V3
   Instead of treating all content uniformly, V3 classifies each PDF page as
   TEXT_RICH / TABLE / IMAGE_ONLY / MIXED. This ensures:
     - Tables use pdfplumber's structured extraction (not raw text dump)
     - Image-only slides/pages go through vision model (no silent data loss)
     - Mixed pages get both text and image descriptions

7. SENTENCE-BOUNDARY CHUNKING WITH OVERLAP
   smart_chunk() splits at sentence boundaries (not fixed character count)
   to preserve semantic units. 50-token overlap ensures retrieval context
   spans chunk boundaries. Tables are never split (kept whole).

8. EMBEDDED QDRANT (NO DOCKER)
   Qdrant runs embedded (storage/qdrant/) — no separate Docker container.
   Simplifies deployment. Drawback: can only serve one process at a time.

9. PERSISTENT CHAT STATE
   Chat messages stored in Zustand (not React local state) so the conversation
   history survives navigation between pages. Only cleared on explicit "Clear".
   Streaming/loading state is ephemeral (local useState) — resets on remount.

10. QUERY CACHE INVALIDATION
    query_cache.clear() is called whenever a new document is ingested.
    This ensures cached answers don't become stale when new knowledge is added.
    doc_id-filtered queries bypass the cache entirely.

11. CONFLUENCE TABLE ENTERPRISE HANDLING
    Confluence tables often use colspan/rowspan for complex layouts.
    _materialize_table() builds a full 2D grid expansion before extracting
    headers and data rows. Multi-row header groups are merged with " / ".
    Produces two chunk types: table_summary (for overview queries) and
    table_row (for data lookup queries).

12. DEDUPLICATION BY CONTENT HASH
    SHA-256 hash of file bytes catches exact duplicates regardless of filename.
    Same filename + different hash → triggers replacement flow.
    Same hash → immediate return of existing doc_id, no reprocessing.

13. LANGUAGE SUPPORT (EN / NL)
    All frontend strings externalised to i18n/en.json + nl.json.
    Chat responses also language-aware: system prompt instructs LLM to respond
    in the user's language. Language detected from i18n locale.
